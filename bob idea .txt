## 🔥 The Real-World Problem

### Context
Every software team — from 5-person startups to IBM-scale enterprises — experiences production incidents. Servers go down, APIs break, deployments fail. But the most damaging part isn't the downtime itself. It's what happens in the 24–72 hours after.

### What Currently Happens (The Pain)
When an incident is resolved, the on-call engineer must:
1. Manually reconstruct the incident timeline from scattered logs, Slack messages, and memory
2. Dig through git history to find the root-cause commit — often across hundreds of recent PRs
3. Write a structured postmortem document from scratch (summary, timeline, impact, root cause, action items)
4. Manually file each action item as a Jira/Linear ticket with appropriate priority and ownership
5. Cross-reference with past incidents — usually by searching Confluence manually, if at all
6. Get the document reviewed and published, often days after the incident

### The Numbers (Industry Data)
- **8–12 hours per postmortem** spent by senior engineers on manual documentation
- **69% of developers** report spending at least 8 hours per week on technical debt (including incident aftermath)
- **20% of their workweek** disappears into firefighting and documentation instead of building
- **23–42% of development time** is wasted dealing with technical debt consequences
- Teams with unmanaged recurring incidents see **30–50% slower release cycles** than those who actively track patterns
- **40% of technical debt incidents** arise from the same class of bugs re-appearing because lessons weren't institutionalized

### The Root Cause of the Problem
Postmortems are not being written because engineers are lazy — they're not being written well because:
- The cognitive load of reconstructing an incident while still mentally exhausted from it is enormous
- No tool reads the codebase with enough context to trace a bug to its introducing commit automatically
- Action items get buried in documents nobody revisits
- There is no systematic cross-referencing of incidents — institutional knowledge lives in senior engineers' heads and leaves when they do
- Tooling exists for creating postmortem *templates* (Blameless, FireHydrant) but none that *fills them in* using code and repo intelligence

### The Consequence
Teams are doomed to repeat the same class of incidents every quarter. The same architectural mistake, the same untested edge case, the same deployment anti-pattern — appearing in disguise under a different ticket number.

## 🏗️ Architecture & How It Works

### Trigger Layer
- Webhook integration with **PagerDuty** or **Opsgenie**
- When a P1/P2 alert is resolved (or manually triggered mid-incident), PostMortem Autopilot activates
- Receives: incident ID, affected services, alert timestamp, duration, alert description

### Automated Pipeline (6 Stages)

```
Incident fires → Bob reads repo → Root cause trace → Draft generated → Tickets filed → Pattern alert
```

#### Stage 1 — Incident Signal Capture
- Pulls structured data from PagerDuty/Opsgenie API: timeline, affected service, runbook links, responders
- Pulls recent deployment history from CI/CD (GitHub Actions / Jenkins / Tekton)
- Pulls relevant log excerpts from observability platform (Datadog / Splunk / OpenSearch)

#### Stage 2 — Bob Reads the Full Repo (Architect Mode)
- Bob ingests the entire repository with full codebase context
- Identifies all services, modules, and dependencies touched by the failing service
- Maps the call graph, data flow, and failure blast radius
- This is the step no other tool can do — Bob understands the *system*, not just the file

#### Stage 3 — Root Cause Trace (Agentic, BobShell)
A BobShell playbook orchestrates three specialized sub-agents in parallel:

- **Agent A — Git Archaeologist:** Runs `git log`, `git blame`, and `git bisect`-style analysis to identify the introducing commit. Cross-references the commit with PR description, reviewer, and CI results at merge time.
- **Agent B — Pattern Matcher:** Scans the diff of the root commit against Bob's knowledge of known anti-patterns, insecure constructs (via Semgrep), and previously seen failure signatures in the incident history store.
- **Agent C — Log Correlator:** Aligns log timestamps with deployment events, feature flag changes, and config updates to produce a precise incident timeline with causal links, not just a list of events.

All agent actions are logged in real time by BobShell — every step is traceable and auditable.

#### Stage 4 — Postmortem Draft Generation (Bob Code Mode)
Bob generates a fully structured postmortem document in your team's preferred format (Confluence, Markdown, Notion template) containing:

1. **Incident Summary** — Plain-English description of what broke, when, how long, and user impact
2. **Root Commit Link** — Exact PR/commit hash that introduced the regression, with author, merge date, and reviewer
3. **Timeline Reconstruction** — Auto-assembled from logs, alert timestamps, deploy history, and responder actions
4. **Impact Quantification** — Estimated users affected, revenue impact window, SLA breach calculation
5. **Contributing Factors** — Structural reasons why the bug wasn't caught (missing test, skipped review, no monitoring on this path)
6. **Action Items with Owners** — Prioritized, specific, assigned fix list (not vague "improve testing")
7. **Prevention Playbook** — Specific tests and monitoring rules Bob writes to catch this exact bug class next time

#### Stage 5 — Jira/Linear Auto-Filing
- Each action item from Stage 4 is automatically filed as a Jira ticket
- Bob assigns: priority label (P1/P2/P3), suggested owner (based on git ownership of affected module), epic link, sprint suggestion
- Zero action items fall through the cracks
- Tickets contain a direct link back to the postmortem section that generated them

#### Stage 6 — Pattern Detection & Institutional Memory
- A vector store (pgvector / Pinecone) holds embeddings of all past postmortems
- Bob's multi-model routing uses a lightweight model for similarity search and Claude for nuanced root cause comparison
- If the current incident matches a prior pattern (same module, same failure class, same contributing factor), Bob surfaces: "⚠️ This is the 3rd incident in 90 days rooted in the authentication middleware. Recommended: architectural review."
- This alert goes to the engineering manager, not just the on-call
